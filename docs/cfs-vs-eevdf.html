CFS vs EEVDF: CPU share, turn length, and deadlines

Both Linux schedulers split the CPU fairly according to nice values. The difference is what else a task can ask for. CFS ties how much CPU a task gets to how long each of its turns lasts, and it has no idea when a task needs to run. EEVDF separates these and gives every turn a deadline.

The core difference

CFS: one knob

Time until your next turn: the rest of the period. No way to ask for sooner.
  • Every ready task gets exactly one turn per period.
  • A smaller share just means a shorter turn, not a sooner one.
  • The next pick is whoever is furthest behind. Nothing in the queue says "I need to run soon".

Two 24 ms periods. B has a small share, so its turn is short, but it still waits out all of A's turn every time.

EEVDF: two knobs

nice
→
CPU share
slice
→
Length of each turn, and so how soon the next one comes
  • Nice still sets the share. The slice is the turn length a task asks for (set per task with sched_setattr from Linux 6.12, otherwise a default).
  • Each request gets a deadline: the moment a perfectly fair CPU would have finished it. A short slice or a big share means an earlier deadline.
  • Among tasks that are owed CPU, the one with the earliest deadline runs next. A task already ahead of its share has to wait, so short slices can't be used to grab extra CPU.

The same task in two separate runs, not two tasks running together. In both runs it gets a quarter of the CPU, and the gaps go to other tasks (not shown). Only the rhythm changes.

Freeze-frame at the cursor

What each scheduler "sees" when it chooses. Positions show how far each task is behind or ahead of its fair share.

CFSone position per task, and nothing else

There are no deadlines here. The leftmost task goes next. A task has no way to tell CFS it needs to run soon.

EEVDFa position and a deadline for each task's current request

The circle is where the task stands now and the flag is its deadline. Tasks in the green area are behind the fair point, so they're owed CPU and may run. Tasks in the grey area are ahead and must wait. Among tasks in the green area, the earliest flag goes next. A shorter slice or a bigger share gives a shorter bar, which means an earlier deadline. The fair point drifts right while any task runs.

Results

    What this model leaves out

    • There is one CPU and every task is always busy. Real tasks sleep and wake up. CFS helped waking tasks with special-case bonus rules; EEVDF handles them with the same deadline logic and, from 6.12, lets short-slice tasks preempt when they wake.
    • Turns end exactly on time. Real kernels usually check at timer ticks unless high-resolution ticks are on.
    • Defaults grow with CPU count, up to 8 CPUs. The CFS period is 6, 18, or 24 ms, and the EEVDF default slice is 0.75, 2.25, or 3 ms.
    • Control groups and task migration between CPUs are not modelled.
