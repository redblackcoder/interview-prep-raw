What is kNN search?

Given a set of points P and a query point q, return the k points in P that are closest to q under some distance metric (Euclidean, cosine, Haversine for the globe…).

Two families of problems share this shape:

  • High-dimensional kNN — vector search / embeddings (recommendations, RAG, image similarity). Dimensions in the hundreds–thousands.
  • Low-dimensional / geospatial kNN — "5 nearest drivers", "restaurants within 2 km". Usually 2D (lat, lng) on a sphere.

The core tension is always the same: a naïve scan is O(N·d) per query. Everything that follows is a way to avoid looking at most of the points by exploiting structure — either a tree that prunes branches, or a grid/curve that maps space to a sortable key so you can use a plain B-tree index.

Brute force — the baseline every system falls back to

Compute the distance to every point, keep a max-heap of size k. Simple, exact, embarrassingly parallel — and the thing you must beat.

Cost: O(N·d) per query, O(N) memory. For 1k points it's instant; for 1B vectors it's a full table scan. That's why we index — but note that GPU brute force (FAISS flat) is still the exact-answer gold standard and is often "fast enough" up to a few million vectors.

Approximate NN (ANN) — when exact is too expensive

In high dimensions, tree pruning collapses (the "curse of dimensionality": everything is roughly equidistant, so no branch can be safely skipped). The industry answer is to give up exactness for a ~95–99% recall and enormous speedups. The dominant structure is HNSW (Hierarchical Navigable Small World) — a multi-layer proximity graph you greedily walk toward the query.

Other ANN families: IVF (inverted-file: cluster with k-means, probe nearest cells), PQ/OPQ (product quantization — compress vectors to bytes), LSH (locality-sensitive hashing). Real systems combine them: IVF+PQ, HNSW+PQ. Products: FAISS, ScaNN, pgvector, Milvus, Weaviate, Qdrant, Pinecone.

Distributed kNN on a lakehouse (S3 / Iceberg)

Now the data is billions of rows sitting as Parquet files in object storage, catalogued by Apache Iceberg. There is no always-on index server — queries run on ephemeral compute (Spark, Trino, DuckDB). Two things make this work:

  1. Partition + prune: never read files that can't contain an answer. Iceberg's manifest metadata stores per-file min/max of each column (a "zone map"). If you store a spatial key column (a geohash/S2/H3 cell, or a space-filling-curve value), the planner skips every file whose key range is outside your query region.
  2. Scatter–gather: the remaining files are scanned in parallel, each producing a local top-k; a final merge step keeps the global top-k. Because top-k is mergeable (a monoid), this parallelizes perfectly.

The critical layout decision: to make min/max pruning effective, physically sort/cluster rows by a spatial key so that nearby points land in the same file. A raw (lat, lng) sort clusters well along latitude but scatters along longitude. This is exactly the problem space-filling curves solve — sort by a single Z-order or Hilbert value and 2D locality is preserved in the 1D file layout. Iceberg's Z-ORDER compaction and Databricks' liquid clustering do this for you. 
-- Iceberg: cluster files along a space-filling curve so zone maps prune well
ALTER TABLE rides WRITE ORDERED BY zorder(lat, lng);

-- Query: bounding-box prefilter (prunes files) + exact distance rank
SELECT id, lat, lng
FROM rides
WHERE lat BETWEEN :latMin AND :latMax      -- min/max prune manifests → skip files
  AND lng BETWEEN :lngMin AND :lngMax
ORDER BY haversine(lat, lng, :qLat, :qLng)  -- exact rank on survivors
LIMIT :k;

kNN on 2D data — locations on Earth

Geospatial kNN is low-dimensional (2D), so pruning works beautifully and answers are exact and cheap. There are two broad philosophies:

1 · Tree-based (recursive space partitioning)

Build a tree that carves the plane into regions. Search descends only into regions that could contain a neighbor, pruning the rest.

kD-treeQuadtreeR-tree

2 · Grid / geohash-based (discretize + encode)

Chop the surface into cells, give each cell a string/integer key, and store points by key. kNN becomes "look at my cell + neighbors" using an ordinary B-tree/hash index.

GeohashS2H3

The distinction blurs at the top: the best grid systems (S2) internally use a tree of cells ordered by a Hilbert curve, and lakehouses combine grid keys with tree-like manifest pruning. We'll build up to why.

kD-tree

A binary tree that splits the point set on alternating axes (x, then y, then x…), each node using the median point as the pivot. Search for the nearest neighbor descends to the leaf containing q, then backtracks, only visiting the other side of a split if the splitting line is closer than the best distance found so far.

Quadtree

Recursively subdivide a square region into four equal quadrants (NW, NE, SW, SE). A cell splits once it holds more than a capacity threshold. Unlike the kD-tree, splits are on space (fixed geometry), not on the data — which makes it simpler to update and naturally adaptive to density: crowded areas get deep subdivision, empty areas stay coarse.

Quadtrees are the workhorse of 2D games, GIS, image compression, and collision detection. The 3D analogue is the octree (eight children).

R-tree

The database index for spatial data (PostGIS, SQLite R*Tree, Oracle Spatial). Instead of splitting space, it groups nearby objects into Minimum Bounding Rectangles (MBRs), then groups those MBRs into bigger MBRs — a balanced, B-tree-like structure where every node is a rectangle enclosing its children. Search descends only into MBRs that intersect the query region. Crucially it handles extended objects (polygons, roads), not just points, and MBRs are allowed to overlap.

Geohash

A geohash turns (lat, lng) into a short base-32 string by recursively bisecting the world. Interleave the bits: odd bits halve longitude (E/W), even bits halve latitude (N/S). Group every 5 bits into one base-32 character. The magic property: shared prefix ⇒ spatial proximity. gcpuv and gcpuu are adjacent-ish; the longer the shared prefix, the closer the cells.

▶ Live: build a geohash bit-by-bit

Click a location. Watch the world get bisected — each step halves the box along one axis and appends a bit; every 5 bits emits a base-32 character. Longer hash = smaller, more precise cell.
hash: —
The kNN recipe: compute q's geohash, then query the prefix + its 8 neighbor cells (the "ring") from a plain B-tree index (WHERE geohash LIKE 'gcpuv%'), and rank the candidates by exact distance.

The gotcha — edge effects: two points can be metres apart but sit either side of a cell boundary, giving totally different prefixes (e.g. crossing the equator or prime meridian flips a high bit). That's why you must always search the 8 neighbors too, and why cell size is uneven near the poles (it's a lat/lng grid, not equal-area). 
Precision:  1 char ≈ 5000 km   |   5 chars ≈ 4.9 km   |   7 chars ≈ 153 m   |   9 chars ≈ 4.8 m

S2 (Google)

S2 fixes geohash's two big flaws — distortion near the poles and the wrap-around/edge problem — by working on the sphere, not a flat lat/lng grid. It projects the sphere onto the 6 faces of a cube, subdivides each face into a quadtree of cells (up to 30 levels, down to ~1 cm²), and — this is the key part — numbers all cells along a Hilbert curve. A cell is a single 64-bit integer (S2CellId) whose ordering keeps neighbors numerically close.

▶ Live: cube-face quadtree ordered by a Hilbert curve

One cube face, subdivided into a quadtree. The Hilbert curve threads through the cells so that consecutive cell IDs are spatial neighbors — letting a range query on a 64-bit integer act as a spatial region query.
cells: 64
Why the Hilbert curve matters here: because cells are numbered along it, a contiguous range of S2 cell IDs corresponds to a compact, roughly-convex patch of the sphere. A region query becomes a handful of integer range scans — perfect for a B-tree, a key-value store, or Iceberg min/max pruning. This is the direct bridge to the space-filling-curve section below.

H3 (Uber)

H3 tiles the world with hexagons (plus 12 pentagons to close the sphere, projected from an icosahedron). Uber built it because hexagons have a property squares don't: all 6 neighbors are equidistant and share a full edge. With squares, diagonal neighbors are farther than edge neighbors and only touch at a corner — which distorts "expand to the next ring" operations used constantly in demand/supply modelling and smoothing.

kNN with H3: index each point by its H3 cell (a 64-bit id). To find neighbors, take q's cell and its kRing(k), fetch points in those cells, rank by exact distance, grow k until you have enough. Hierarchical: every cell has a parent at a coarser resolution for cheap roll-ups.

H3 vs S2: H3 = uniform hex neighbors, great for analytics/ML aggregation; S2 = clean hierarchy + Hilbert range scans, great for indexing and covering regions with cell ranges.

S2 vs H3 — exact vs approximate hierarchy

Both S2 and H3 do the same two-step move: project the sphere onto a polyhedron, then tile each flat face and refine into finer resolutions. The deep difference is how the resolutions nest — and it explains why each system is good at what it's good at.

What "project, then subdivide with a quadtree" really means (S2)

Two distinct steps:

  • Project (sphere → 6 flat squares). You can't lay a regular recursive grid on a curved sphere. So S2 wraps the globe in a cube and pushes each surface point out to one of the 6 faces, turning a point into (face 0–5, u, v) — plain flat coordinates on a unit square. (A nonlinear transform then squeezes the corner-vs-center area distortion from ~5× down to ~2×.) One hard curved problem becomes six easy flat-square problems.
  • Quadtree each square. Recursively split each face into 4 quadrants, up to 30 levels, down to ~1 cm².
Why a quadtree and not "just chop the face into a flat grid of cells"? Because a quadtree is chopping into cells — it just keeps every resolution at once, nested. At any single level L, the quadtree's cells already are a uniform 2ᴸ×2ᴸ grid; a flat grid is one horizontal slice of it. Keeping the whole nested hierarchy buys three things a single-resolution grid throws away:
  1. Containment = prefix. Exact 4-way splits make a cell's ID a literal prefix of all its descendants'. The 64-bit S2CellId = 3 bits face + 2 bits/level (quadrant path) + sentinel. Parent/child is a bit-shift.
  2. A region = a few contiguous integer ranges. Number leaves along a Hilbert curve and any parent cell covers a contiguous run of leaf IDs → region queries become WHERE cellid BETWEEN lo AND hi on a B-tree.
  3. Adaptive covering. Cover a polygon with big cells inside and small cells on the boundary — only possible because levels nest.

Does H3 build a tree too?

First, a clarification: after projection H3's face is a triangle, not a hexagon. H3 projects onto an icosahedron (20 triangular faces); the hexagons are the cells tiled on top, not the faces. (Exactly 12 cells must be pentagons — at the icosahedron's vertices — because Euler's formula forbids tiling a sphere with hexagons alone.)

H3 does have a parent/child hierarchy and a path-of-digits ID — but it refines aperture 7 (each level has ~7× the cells), and 7 hexagons cannot exactly tile 1 hexagon. To make ~7 children fit, the child grid is rotated ≈19.1°, so children straddle parent boundaries. The hierarchy is therefore approximate: a digit-prefix is not an exact region, so H3 gets no clean range-scan trick and roll-ups between resolutions are inexact.

Z-order (Morton) curve

Now the punchline. Geohash, S2, and lakehouse clustering all rely on turning 2D coordinates into a single sortable number that preserves locality. A space-filling curve visits every cell of a grid in an order that keeps spatially-near cells near in the 1D sequence.

The Z-order curve does this by bit-interleaving: take the binary of x and y and alternate their bits. x=0ba₂a₁a₀, y=0bb₂b₁b₀ → key 0bb₂a₂b₁a₁b₀a₀. Sorting by this key traces a recursive "Z" / "N" shape. This is literally what a geohash is — interleaved lat/lng bits, then base-32 encoded.

click a cell
Z-order's weakness: it has big jumps. At the end of one "Z" the curve leaps across the whole quadrant to start the next — so two cells that are far apart in 2D can be adjacent on the curve, and vice-versa. These discontinuities hurt range-query efficiency (a query box maps to many disjoint key ranges). Its saving grace is that it's dirt cheap to compute (just bit ops), which is why it's everywhere.

Hilbert curve

The Hilbert curve is the gold standard for locality. It fills the same grid but has no long jumps: every step moves to an edge-adjacent cell. It achieves this by rotating and reflecting the sub-curve in each quadrant so the ends line up. The result: cells close on the curve are almost always close in 2D, which is why S2 uses it and why Iceberg/Databricks Z-ordering is increasingly replaced by Hilbert clustering.

How space-filling curves supercharge grid/geohash approaches

Tie it together — this is the "why it all works" section interviewers probe:

  1. They collapse 2D into 1D without a specialized index. A curve value is a single number/string, so you can use the most battle-tested index on Earth — a B-tree — for spatial data. Geohash strings, S2 cell IDs, and H3 indexes are all "coordinate → 1D key" encodings.
  2. Locality preservation makes range scans mean something. Because near-in-space ⇒ near-in-key, a bounding-box query becomes a small set of contiguous key ranges (WHERE key BETWEEN lo AND hi), and a kNN query becomes "scan my cell + neighbor cells". No curve locality ⇒ a box would scatter across the whole key space.
  3. They make data-skipping work in a lakehouse. Sort/cluster Parquet files by a Hilbert/Z value and each file's min/max covers a compact spatial patch. Iceberg/Delta then prune 90%+ of files by metadata alone — the distributed scatter-gather from earlier only touches the files that can contain answers.
  4. Z-order = cheap but jumpy; Hilbert = pricier but best locality. Z-order is pure bit-interleaving (what a geohash is under the hood); Hilbert needs per-quadrant rotation but eliminates the long jumps, giving fewer, longer contiguous ranges — hence S2's choice and modern clustering's move toward it.
One-line mental model: Trees prune by descending only into regions that matter. Grids + space-filling curves turn "regions that matter" into "a few contiguous ranges of one sortable key" — so any B-tree, KV store, or min/max-pruned Parquet layout becomes a spatial index.

Caching kNN query results

kNN queries have one nasty property for caching: the query point is a continuous coordinate. Two users standing 1 metre apart produce different (lat, lng) — so a cache keyed on the raw point has a ~0% hit rate. The whole trick is to quantize the query to a cell so that many nearby queries collapse to the same cache key.

The general pattern (works for every scheme)

cache_key = cell_id( quantize(query_point, granularity) )        // + maybe k, filters
value     = candidate set for that cell (+ its neighbor ring)    // the expensive part

on query:
  1. key   = cell_id(q)                    // derive key purely from q — no index lookup
  2. cands = cache.get(key)  ?? (fetch candidates from index; cache.put(key, cands, TTL))
  3. return exact top-k by ranking `cands` against the *precise* q   // cheap, in-memory
Cache candidates, not the final answer. The exact k-nearest depends on the precise query location, so you cache the cell's point set (stable across everyone in the cell) and do the final exact ranking per-request in memory. This gives high hit rates and exact results. Granularity is the classic dial: coarser cell → more cache hits but a bigger candidate set to re-rank; finer cell → precise but low hit rate.

Geohash — the easy case

The cache key is the geohash truncated to a chosen precision, e.g. "gcpuv" (5 chars ≈ 5 km cell). It's derivable from q with pure math, it's a natural string key for Redis/Memcached, and the "granularity" knob is just the prefix length. Cache the candidate set for gcpuv plus its 8 neighbors (the edge-effect ring). Invalidation: when a point in cell gcpuv moves/changes, evict gcpuv and the 8 neighbor keys.

Quadtree — the tricky case, and the key insight

A quadtree has no fixed global grid: leaf cells are variable-sized (deep where dense, shallow where sparse) and the tree reshapes as points are inserted/deleted. So "cache keyed on the leaf a query lands in" is fragile — the same coordinate can land in a different leaf tomorrow, and cell boundaries aren't stable.

The insight: a quadtree cell has a canonical address — the sequence of quadrant choices from the root (NW=0, NE=1, SW=2, SE=3). That path string "0-1-3-2" is literally a base-4 Morton / Z-order code. So the quadtree already gives you a hashable spatial key — the same space-filling-curve idea from earlier. You get two viable strategies:

Click a cell. Its cache key is the root-to-cell quadrant path (0=NW,1=NE,2=SW,3=SE). Use the slider to pick a fixed granularity level — the key is truncated to that depth, giving a geohash-style stable grid on top of the (mutable) tree.
cache key: —
  1. Fixed-level key (recommended for caching). Don't key on the actual leaf. Pick a fixed depth L and truncate the quadrant path to L digits: quad_prefix(q, L) = "013". This decouples the cache key from the mutable deep structure — you've effectively imposed a stable geohash-like grid on top of the quadtree, purely for caching. Same knob, same neighbor-ring rule, same eviction as geohash. In practice: use the tree for the index, use a fixed-level Morton/quadkey for the cache.
  2. Node-level cache with versioned invalidation. If you truly want to cache at real node granularity, store a cached candidate list on each node, tagged with a version counter for that subtree. Any insert/delete bumps the version of every ancestor node up to the root (O(depth)). A cache entry is valid only if its stored version matches the node's current version — so a mutation anywhere in a subtree invalidates exactly the cached results that covered it, without touching unrelated cells. This is the general "path-to-root invalidation" trick for any hierarchical index.
The unifying takeaway: caching a spatial query requires a stable, query-point-derivable key at a fixed granularity. Geohash/S2/H3 hand you one for free (that's the whole point of the grid). A quadtree's variable leaves don't — so for caching you either truncate its quadrant path to a fixed level (turning it into a fixed grid = Morton prefix, exactly like a geohash) or version-invalidate per node. This is another face of why space-filling curves matter: a stable 1D key is what makes both indexing and caching tractable.

Cross-cutting concerns for any scheme

  • Moving objects (drivers, players): use short TTLs or event-driven eviction on location updates; often only the candidate cell membership is cached, with live positions fetched fresh.
  • Negative caching: cache "cell is empty / fewer than k" to avoid re-scanning sparse regions.
  • Two-tier: per-cell candidate cache (shared) + optional per-exact-query result cache with tiny TTL for hot identical requests.
  • Key should include anything that changes the answer: granularity/prefix, k, and any filters (open-now, category), or you'll serve wrong results across filter variants.
