Your algorithm vs Dijkstra: the counterexample

Heap of edges keyed by raw weight w, relax with dist[u] + w, add a node to the set the first time an edge reaches it.

The bug: the heap pops edges in order of raw weight, which has nothing to do with order of distance from S. So a node can join the "done" set while its distance is still too big. Its outgoing edges then get popped using that too-big dist[u]. When the node's distance gets fixed later, nobody pushes its outgoing edges again, so the nodes after it keep the wrong value.

The graph

Edges (directed): S→X = 2, X→A = 2, S→A = 3, A→T = 1.
True shortest distances: X = 2, A = 3 (direct edge), T = 4 (S→A→T).

The trap: the direct edge S→A (3) is heavier than each edge on the detour S→X→A (2, 2), but lighter than their sum (4). Sorting by raw weight takes the detour first.

Your algorithm

heap key = w

Dijkstra (same edge heap, one change)

heap key = dist[u] + w

The one-line fix

for (v, w) in adj[u]:
-    heap.push((w,           u, v))   # your version: order by edge weight
+    heap.push((dist[u] + w, u, v))   # Dijkstra: order by distance from S
...
(key, u, v) = heap.pop()
if v in done: continue                # stale entry, v already has its final distance
dist[v] = key; done.add(v)

Once the key is dist[u] + w, keys come out of the heap in non-decreasing order. With non-negative weights, the first time you pop an edge into v its key really is the shortest distance to v. That guarantee is the whole proof of Dijkstra. Raw weights don't give you that guarantee, so the "done" set can lock in a wrong value.

Why it worked on the GeeksforGeeks graph

On that graph, the edge that first reaches each node is already on that node's shortest path. So no node is ever locked in too early, and the bug never shows. To break it you need all three of these:

  1. A node A first reached by a path of several small edges whose sum is large (S→X→A = 2+2).
  2. A shorter path to A that uses a heavier single edge (S→A = 3), so it gets popped later.
  3. A cheap edge out of A (A→T = 1) that gets popped between those two events, which carries the wrong dist[A] forward.

Why Gemini's counterexample didn't work

  • It changed your algorithm. It said you were "running Prim's". But Prim's stores key[v] = w and never adds up a path. You do add up dist[u] + w. What you wrote is a mix: Prim's pop order with Dijkstra's relaxation. That is a different algorithm.
  • It never ran its own example. In the S/A/B/C graph, C is first reached through its true shortest path (S→A→C = 2). Condition 1 above never happens, so nothing breaks. The answer it gave was fine; it just said "it can force detours" without showing one. You caught that.
  • It gave the textbook answer to a different question. "Dijkstra vs Prim" is the usual confusion, so it explained that, instead of tracing what you described. Free/Flash-tier models tend to do this. They don't check a claimed counterexample by stepping through it, and they rarely build an adversarial input. Its second reply ("you've reinvented Dijkstra exactly") and its third ("it's Prim's") also contradict each other.

Tip for next time: paste your algorithm as code and ask it to "give a graph where this returns a wrong distance, and trace the heap step by step to prove it." Asking for a trace makes it check the example.

Side note: "just re-push A's edges when dist[A] improves"

That gives correct answers, because every improvement eventually reaches the nodes after it. But it is now a label-correcting algorithm, like Bellman-Ford/SPFA, not Dijkstra. A node can be improved many times, and on bad inputs the work can blow up exponentially. Ordering by dist[u] + w fixes it properly: each node is settled once, in O(E log V).
