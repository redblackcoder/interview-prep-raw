Technical Study Guide

Networking: OSI, HTTPS & VPN

A ground-up walkthrough of how a byte travels the network — from the 7-layer model, through the complete HTTPS handshake and wire format, to why encrypted transport still isn't enough, ending with a VPN built one layer at a time.

How to read this guide
Each section builds on the previous one. The mental model to hold: every security property has to be placed at a specific layer. HTTPS secures the payload at layers 5–7; a VPN secures the envelope at layer 3. Understanding which layer owns which guarantee is the whole game.

1. The OSI 7-Layer Model

The Open Systems Interconnection (OSI) model is a conceptual framework that splits network communication into seven layers. Each layer talks only to the layer directly above and below it, and each has a single well-defined job. This separation is why you can swap Wi-Fi for Ethernet (Layer 1/2) without rewriting your web app (Layer 7).

Data flows down the stack on the sender (each layer wraps the data in its own header — encapsulation) and up the stack on the receiver (each layer strips its header — decapsulation). A layer on the receiver only ever reads the header its peer layer wrote.

1.1 Encapsulation — how the layers nest

When you send an HTTPS request, the browser hands the HTTP message down. Each layer prepends (and Layer 2 also appends) its own header, treating everything above as an opaque payload. By the time it hits the wire it's a set of Russian nesting dolls:

Ethernet Header (L2)Frame · MAC src/dst, EtherType
IP Header (L3)Packet · IP src/dst, TTL, proto
TCP Header (L4)Segment · ports, seq/ack, flags
TLS Record (L5/6)encrypted envelope
HTTP Request (L7)GET /path · Host: · Cookie:
“the actual data” — your JSON body, form fields, etc.
+ Ethernet FCS trailer (checksum)

Notice where TLS sits: it wraps the HTTP layer but is itself wrapped by TCP/IP/Ethernet. This is the crux of Section 3 — the IP and TCP headers (who's talking to whom, on what port) are outside the encrypted envelope and are visible to everyone on the path.

1.2 OSI vs the real-world TCP/IP model

OSI is the teaching model; the internet actually runs on the leaner TCP/IP model. The mapping:

OSI (7 layers)TCP/IP (4 layers)Real protocols
7 App · 6 Presentation · 5 SessionApplicationHTTP, TLS, DNS, gRPC
4 TransportTransportTCP, UDP, QUIC
3 NetworkInternetIP, ICMP, IPsec
2 Data Link · 1 PhysicalLink (Network Access)Ethernet, Wi-Fi, ARP
Where does TLS live?
TLS is the classic "it depends" answer. Functionally it provides Presentation (6) services (encryption) and Session (5) services (session establishment/resumption), while running over TCP at Layer 4. In interviews: "TLS sits between the transport layer and the application, providing session + presentation duties (L5/6)." QUIC blurs this further by folding TLS 1.3 directly into an L4 transport over UDP.

2. HTTPS in Full Detail

HTTPS = HTTP over TLS. The HTTP semantics are unchanged; every byte is simply carried inside an encrypted TLS tunnel running over TCP (port 443). TLS delivers three guarantees:

Confidentiality

An eavesdropper sees only ciphertext. Achieved with a symmetric cipher (AES-GCM, ChaCha20) using a key negotiated during the handshake.

Integrity

Tampering is detected. An AEAD cipher produces an authentication tag over every record; a flipped bit fails verification.

Authentication

You're really talking to bank.com, not an impostor. Proven by an X.509 certificate signed by a trusted CA.

Forward secrecy

Ephemeral (EC)DHE keys mean a stolen server private key cannot decrypt yesterday's captured traffic.

2.1 Before TLS: DNS resolution & the TCP 3-way handshake

Typing https://bank.com triggers three sub-steps before a single byte of application data moves:

① DNS lookup (L7 over UDP/53): resolve bank.com → 203.0.113.10. Note: classic DNS is plaintext — the first leak we'll revisit in §3.

② TCP 3-way handshake (L4): establish a reliable byte stream. SEQ numbers synchronize both directions.

Why ephemeral keys (ECDHE)?
The *KeyExchange messages carry ephemeral Diffie-Hellman public keys generated fresh for this connection. The shared secret is computed independently by each side and never transmitted. Because the private halves are thrown away afterward, capturing the traffic + later stealing the server key still won't decrypt it — this is forward secrecy. The certificate's RSA/ECDSA key is used only to sign the exchange, proving the server owns it — not to encrypt the secret.

2.3 TLS 1.3 handshake (1 round trip)

TLS 1.3 (RFC 8446, 2018) is the modern default. It cut the handshake to 1 RTT by making the client guess the key-exchange parameters up front, and it removed every legacy/insecure option (static RSA key exchange, RC4, CBC MACs, compression, renegotiation).

2.4 Anatomy of a cipher suite

A TLS 1.2 cipher suite name encodes every cryptographic choice. Decoding one:

TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256

    └─────────────────────────────── ECDHE  : key exchange (Elliptic-Curve Diffie-Hellman Ephemeral)

2.5 PKI & the certificate chain of trust

Authentication rests on Public Key Infrastructure. Your OS/browser ships with a trust store of ~150 root Certificate Authority (CA) public keys. Trust chains downward:

The browser verifies each signature up the chain until it reaches a root it already trusts.

What the browser actually checks when it receives the Certificate message:

  1. Signature chain — each cert is signed by the next one up; the leaf ultimately chains to a trusted root.
  2. Hostname match — the requested host appears in the cert's Subject Alternative Name (SAN). (The old Common Name field is deprecated.)
  3. Validity window — notBefore ≤ now ≤ notAfter.
  4. Revocation — not revoked, via OCSP / OCSP stapling / CRL.
  5. Proof of possession — in the handshake the server signs with the cert's private key (TLS 1.3 CertificateVerify), proving it truly owns the cert, not just a copy of it.
The trust model's soft underbelly (preview of §3)
You trust every CA in the store equally. If any one of ~150 CAs is compromised or coerced, it can mint a valid bank.com certificate. This has happened (DigiNotar, 2011). Mitigations: Certificate Transparency logs, CAA records, HSTS, and public-key pinning.

The one sentence to remember from §2
Everything from the TCP header outward — your IP, the server's IP, the port, packet sizes and timing — is plaintext metadata. TLS encrypts only the innermost payload. Hold that thought.

3. Why HTTPS Isn't Enough

HTTPS is excellent at what it does — but it secures a single application session's payload, nothing more. It was never designed to be an access-control or network-security system. Companies add private networks + VPNs because HTTPS leaves five gaps:

3.1 What TLS does not protect

1 · Metadata & the envelope

The IP/TCP headers are outside the encryption. Anyone on-path (your ISP, coffee-shop Wi-Fi, a transit AS, a nation-state) sees who you talk to, when, how often, and how much — even if not what.

2 · Hostname leakage

Plaintext DNS queries and the TLS SNI field both reveal bank.com before encryption kicks in. (DoH/DoT and Encrypted ClientHello help, but aren't universal.)

3 · No network access control

TLS authenticates the server to the client. It does nothing to stop the entire internet from reaching your internal admin panel, database port, or staging box. If it has a public IP, it's being scanned right now.

4 · Fragile trust anchors

The ~150-CA trust model, corporate TLS-inspection proxies, or a single mis-issued cert can enable a valid-looking MITM. TLS trusts any CA equally.

5 · Per-service, not per-network

Every service must implement, configure, patch, and correctly enforce TLS + authn/authz on its own. Miss one — a legacy service, an internal metrics endpoint, a misconfigured mTLS — and it's exposed.

6 · Endpoints & the app itself

TLS protects data in transit, not a compromised client, a phished credential, XSS, or a malicious server. "The lock icon" ≠ "safe."
The reframing
HTTPS answers "is this conversation private and is the server who it claims to be?" It never answers "should this person even be allowed to reach this server at all?" That second question is a network question — and it belongs at Layer 3, which is exactly where a VPN operates.

3.2 A concrete attack scenario

Let's make gap #3 painfully concrete. Acme Corp runs an internal Kibana dashboard for engineers. It's "secured" — served over HTTPS with a valid cert and a login page. To let staff use it from home, ops assigned it a public IP and opened :443. HTTPS is on, so it's safe… right?

Walk through why HTTPS was irrelevant at each step:

  1. Discovery (①–②): A public IP is discoverable in minutes — the entire IPv4 space is scanned continuously. TLS even helps the attacker: the certificate's SAN and the response reveal the hostname and software version. Encryption doesn't hide existence.
  2. Exploitation (③): The vulnerability is in the application, above TLS. The attacker completes a perfectly valid TLS handshake and sends a malicious request inside the encrypted tunnel. TLS faithfully protects the attacker's packets from eavesdropping — it has no opinion on their content.
  3. Lateral movement (④–⑤): This is the real damage. Because the box lives on a flat internal network with no segmentation, one foothold reaches the database, secrets, and neighboring hosts. HTTPS operates per-connection; it has zero concept of "this actor shouldn't be inside my network."
  4. Exfiltration (⑥): Data leaves over :443, indistinguishable from legitimate web traffic — and encrypted, so payload-inspecting defenses see nothing.
Root cause
The server was reachable by everyone. HTTPS secured the pipe but never asked "who is allowed to open a pipe at all?" The fix isn't more encryption — it's removing the service from the public internet and forcing every connection through an authenticated network gateway. That gateway is a VPN.
The two principles a VPN restores
1 · Network-level access control — internal services get private IPs, unreachable from the internet; you must first be on the network to reach them. 2 · Confidential + authenticated transport for the whole IP flow — not per-app, but for every packet, including the metadata HTTPS leaks.

4. Building a VPN, Layer by Layer

4.1 The goal

A Virtual Private Network creates a virtual private link across the shared, untrusted public internet, so that a remote client behaves as if it were physically plugged into the corporate LAN. We want:

  • A remote laptop to reach private internal servers (10.0.0.0/8) that have no public IP at all.
  • Every packet — headers included — encrypted & authenticated as it crosses ISPs.
  • Only authenticated, authorized devices to get onto the network.
  • Optionally, the client's public internet traffic to also route through the corporate egress (full tunnel).

We'll construct this from nothing, adding one capability per layer. Each step exists to defeat a specific threat.

4.2 The build

1
Tunneling / Encapsulation
Threat solved: private IPs aren't routable on the internet

Our internal server is 10.1.2.3 — an RFC 1918 private address that no internet router will forward. So we encapsulate: wrap the client's original IP packet (destined for 10.1.2.3) as the payload inside a new "outer" packet addressed to the VPN gateway's public IP.

OUTER IP headersrc=client public IP → dst=VPN gateway public IP
VPN/tunnel header(ESP / WireGuard / etc.)
INNER IP headersrc=10.8.0.2 → dst=10.1.2.3
original TCP/TLS/HTTP payload…

The public internet only ever sees the outer packet: "traffic from a client to the gateway." The private destination is hidden inside. This is the single most important VPN concept — a packet within a packet. But right now the inner packet is plaintext. On to encryption.

2
Encryption — confidentiality
Threat solved: ISPs / on-path attackers reading the tunnel

Before encapsulating, we encrypt the entire inner packet with a symmetric AEAD cipher (AES-256-GCM or ChaCha20-Poly1305). Now the outer packet's payload is ciphertext. Crucially — unlike HTTPS — this hides the inner IP header too. An observer sees only client → gateway; the real source, destination, ports, and data are all inside the encrypted blob.

This directly closes HTTPS gap #1 & #2
The metadata that TLS leaked (which internal host, which port) is now encrypted, because it's part of the payload of the outer packet.
3
Authentication & Integrity
Threat solved: forged packets, tampering, replay

Encryption alone doesn't prove who sent a packet or that it wasn't altered. We add:

  • Message authentication (AEAD tag / HMAC) over each packet — a modified bit fails verification and the packet is dropped.
  • Peer authentication — the gateway must prove the client is an enrolled device (and vice-versa) using pre-shared keys, certificates, or public keys.
  • Anti-replay — a sliding sequence-number window rejects captured-and-resent packets.

Together, confidentiality + integrity + authentication is the same triad as TLS — but applied to whole IP packets at Layer 3, for every protocol, not just one app's stream.

4
Key Exchange
Threat solved: agreeing on keys over an open channel + forward secrecy

Where do the symmetric keys come from? An authenticated Diffie-Hellman exchange, exactly like TLS. IPsec calls this phase IKE (Internet Key Exchange); WireGuard uses a fixed Noise-protocol handshake.

  • Ephemeral (EC)DH → forward secrecy: compromising a long-term key doesn't decrypt past sessions.
  • Periodic rekeying → limits how much data any single key protects.
  • The peers' long-term identity keys authenticate the DH exchange, binding "this key material" to "this enrolled device."
5
Virtual Interface (TUN/TAP)
Making the OS actually send traffic into the tunnel

For applications to transparently use the VPN, the OS needs a network interface that looks real but pipes packets into our encrypt-encapsulate engine. That's a TUN device (a virtual L3 interface, e.g. utun0/wg0).

# the client gets a virtual interface with a private VPN-network IP
utun0: inet 10.8.0.2  # assigned by the gateway on connect

# flow of one packet:
app → kernel routing → utun0 → VPN process: encrypt + encapsulate
    → real NIC (eth0) → internet → gateway → decap + decrypt → internal LAN

TUN = L3 (IP packets) TAP = L2 (Ethernet frames) — TUN is the norm for remote-access VPNs.

6
Routing — split vs full tunnel
Decide which traffic enters the tunnel

The gateway pushes routes to the client, controlling what goes through the VPN:

Split tunnel

Only corporate subnets (10.0.0.0/8) route through the VPN; Netflix/personal traffic goes direct. Faster, less gateway load — but the endpoint straddles two networks (a risk). 
# route only internal ranges
10.0.0.0/8   → utun0
0.0.0.0/0    → eth0 (direct)

Full tunnel

All traffic (0.0.0.0/0) goes through the gateway, which becomes the client's egress. Enables uniform monitoring/filtering & hides the client's real IP — the requirement for "route public traffic through corporate too." 
# default route captured
0.0.0.0/0    → utun0
<gateway IP> → eth0 (so the tunnel itself can reach out)
7
The Gateway, DMZ & segmentation
Where the tunnel terminates — and what it's allowed to reach

The VPN gateway (concentrator) is the only public-facing piece. It sits in a DMZ behind the edge firewall, which permits only the VPN port inbound (e.g. UDP/51820) and drops everything else. After decryption the gateway forwards inner packets to the internal network — but a hardened design does not grant flat access:

  • Firewall / ACLs restrict which internal subnets & ports a VPN client may reach (defeats the lateral-movement step from §3.2).
  • Microsegmentation — the finance VPN pool can't touch the k8s control plane, etc.
  • NAT — internal replies are routed back to the client's VPN IP.
  • DNS — the gateway pushes internal resolvers so wiki.corp.internal resolves (and internal DNS never leaks to public resolvers).

Mapping back to the build
Every protocol implements the same seven steps — they differ in how. IPsec's ESP = steps 1–3, its IKE = step 4. OpenVPN reuses the TLS machinery from §2 as its step-3/4 engine (which is why it can hide on port 443). WireGuard hard-codes steps 2–4 into a tiny fixed handshake.

4.4 The full architecture

Internal servers have no public IP. The gateway is the sole entry point; segmentation ACLs limit reach even after authentication.

4.5 End-to-end packet walkthrough

The remote laptop opens the internal wiki, https://wiki.corp.internal. Watch a single request — note that HTTPS and the VPN operate simultaneously at different layers:

The payoff: defense in depth
There are now two independent encryption layers. The inner TLS gives true end-to-end app security (even the VPN gateway can't read the HTTP body). The outer VPN gives network-level access control + metadata privacy + authenticated admission. Re-run the §3.2 attack now: the attacker scanning the internet finds only the gateway's single hardened UDP port — 10.1.5.4 doesn't exist to them. No admission → no application to exploit → no lateral movement.

4.6 Beyond the VPN: Zero Trust (ZTNA)

The classic VPN has one weakness: it's perimeter-based. Once you're on the tunnel, you're "inside," and segmentation is the only thing limiting you. If a laptop is compromised, the attacker inherits broad network access. Modern architectures evolve the model:

Traditional VPNZero Trust Network Access (ZTNA)
Trust modelTrust the network: "inside = trusted""Never trust, always verify" — no implicit trust
GrantsAccess to network subnetsAccess to specific applications only
Check frequencyOnce, at connect timeEvery request: identity + device posture + context
ExposureGateway is a known public endpointApps hidden behind an identity-aware proxy/broker
Lateral movementPossible within reachable segmentDenied by default — each app is isolated

ZTNA (e.g. identity-aware proxies, mTLS service meshes, "BeyondCorp") applies the same layered discipline we built — encapsulate, encrypt, authenticate, authorize — but shifts the authorization decision from "which network are you on" to "who are you, on what device, requesting which specific app, right now." It's the logical endpoint of this guide: security must be enforced explicitly at every layer, per request — not assumed from position.

Interview one-liners

OSI

7 layers; data encapsulated top-down, each layer adds a header. Know PDU names: Data→Segment→Packet→Frame→Bits.

HTTPS

HTTP over TLS. TLS 1.3 = 1-RTT, mandatory forward secrecy via ECDHE, cert authenticates server, AEAD gives confidentiality+integrity.

HTTPS gap

Encrypts payload, not the envelope. Leaks metadata/SNI, provides no network access control — a public service is still attackable over valid TLS.

VPN

Encapsulate (packet-in-packet) + encrypt + authenticate at L3. Private services get no public IP; the gateway is the single authenticated door. ZTNA is the per-app evolution.
