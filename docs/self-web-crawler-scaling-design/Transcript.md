To start off to design a web crawler, let's look at some of the functional and non-functional requirements that we have:
- We have to discover web pages for our crawler to crawl.
- When we find a web page we have to download the content and find the links in there to discover further web pages to crawl.
- Downloading the content can be both static and dynamic in the sense that are we just doing an HTTP GET and getting the content and parsing it or are we also going to run JavaScript on the page to render the dynamic content on it?
- We are talking about some kind of headless browser for this interview setting.
- I'm just going to focus on the static content.
- Once we have that and we store the content somewhere, we can do further processing on the content, like normalizing it and removing HTML tags so that it is ready for the indexing pipeline.
- Again for this interview setting I'm going to not talk about normalizing the content. I'm also only going to focus on the text content, images, videos, and that kind of stuff, so just text-based crawling.
- Some other requirements will be how often we want to refresh a page. Suppose we have a web page we crawled. When should we crawl it next? Some pages will never change or will change very infrequently so they could be based on a monthly cycle. There could be pages which change frequently so maybe they are based on a weekly cycle or a daily cycle. There might be certain sources which need to be crawled every minute. Let's say we have integration with the Twitter API so crawling new tweets every minute or some news portal which is producing news articles very fast so we have to crawl them. That is another kind of non-functional requirement.
- I would say how often we want to refresh a page. Generally crawlers have to follow a robot.txt that will tell crawlers which pages you can crawl, which pages you cannot crawl, when you are crawling, how fast you can crawl, and all those kinds of things. For this one, for this interview discussion, I'm going to not get into robot.txt for now. If we have time in the end we can discuss that.
- Another part is scale: how many documents are we thinking of crawling every hour, every second? I think that's the most important one.
- How big of an index it is for the storage. I'm going to offload it to an object store and I'm going to assume that we have elastic storage in our object store, like S3, that we can utilize. That is not the central point of this design discussion. I'm going to focus more on scaling the crawling aspect of it and how we can crawl, let's say, a 10,000-document-per-second or 100,000-document-per-second crawl rate.

Let me start with something very simple and then we can see how we make it scale and ensure all our requirements are met. If I start with something simple, let's say I have one single-box crawler. It gets a list of URLs as input and it produces a bunch of documents as output. If I focus on a single URL in the input then that URL is basically a source. If I look at all the interconnected web pages then this URL is like the source node in the graph of these interconnected web pages. We have to do a graph walk from this source URL and find all the connected documents from it and produce the content for all of them. We are doing basically a graph traversal using DFS or BFS.
Since to crawl the web pages we first have to download the web page so that we can look at the content and find the links, we will go with BFS. I think that's what will make sense.

For a web page once we download it, we find all the URLs and we put all those URLs into a queue. We then keep iterating over those in the queue. That way, using the regular BFS algorithm, we avoid duplicate URLs in the queue. Even if our input URL batch can link to the same web pages in the graph, we will only crawl it once using the BFS algorithm, which requires maintaining a hash set.

Basically we need a hash set so that we can keep track of all the URLs that we have seen and we have put into the queue for crawling. In a single-server or single-crawler design we have one crawler holding a hash set in the memory and a queue in the memory. It gets an input batch and it produces the output content for each URL that it gets from the queue. It will perform an HTTP GET on the Internet, download the content, and then write that content to a document store.

Now let's see how something this simple can meet our scaling needs and other non-functional requirements because this is very simple and satisfies our requirements. If we are talking about 10,000 to 200,000 documents per second, one box cannot do it. We have to distribute our load across multiple workers and then when we have multiple workers each cannot have its own queue and hash set because then they will not know anything about other workers and what they are doing and they will end up doing a lot of duplicate work.

The second thing that we also think about is the resilience and resiliency of the design: how do we ensure that if these workers crash they recover the work they don't redo the work or, worse, don't lose the work? Those are, I think, two major things that we have to think through in the design before we say, "Okay the system is a distributed crawling system that can support a huge volume of documents to be crawled."
So let's first talk about how to move our queue into a resilient, persisted, distributed system. We can use Kafka to model the queue so that different workers, each being a producer and consumer of the topic, can read from and write to the topic. It will fetch a URL from the topic and write it back after downloading the content and reading all the links from it. The Kafka topic will be partitioned so that multiple workers can consume from it in parallel without any duplicate message being processed.

Also our other requirement is that some web pages require a faster turnaround time and some require a slower turnaround time. To support that kind of requirement and payload I will go with having multiple topics. There will be a Kafka topic which is used for real-time crawling only so we do not block that queue with documents which can wait a day to be crawled. We can have different tiers of Kafka topics, like daily, weekly, and real time, that we can use to distribute the work and make sure that throughput and the churn rate of the documents that we put in that queue are suitable for the needs.

Second for the hash set we can use Redis that supports a persisted hash set. Redis is in memory so the persistence is based on a snapshot that it can do every so often, I think maybe in a few seconds. We have an RPO of around a few seconds so it is possible that some URLs that we put into the hash set may be lost in a window of, say, a couple of seconds. That is the trade-off that we can live with to have some work getting duplicated across the workers in lieu of utilizing the high throughput, scalability, and low latency of the Redis cluster.

The Redis cluster again will be sharded by the URL. Let's take an example of two workers. They are taking the messages out from Kafka partitions so they are concurrent workers or part of a consumer group. Worker one takes URL 1 from partition one and worker two takes URL 2 from partition two. Let's say URL 1 links to URLs 2, 3, 4, and 5 and for worker two URL 2 links to 3, 6, and 7. Now we have the URL 3 that needs to be crawled in the future on both the workers. How do we avoid duplicates getting into the queue?

When worker one is passing the content, it will put all these URLs into the Redis hash set before it pushes them to the queue. To do so it will issue a batch put for those URLs into Redis. It is an atomic operation. All these URLs will go into Redis once and then when worker two comes and tries to do a batch push of its set of keys, because Redis is single-threaded for a particular shard, it will ensure serialized isolation between these workers. The key which is already in there for worker two will be rejected and only the keys which are unique to worker 2 will get persisted.

Now we have this design of our Kafka cluster having many partitions, our Redis cluster having many shards, and then we have these stateless workers, which basically will have the same number as the number of partitions in the Kafka queue because that's the maximum number of concurrent work we can support in the design.

And each of these workers is doing the work on their machine to download the content, pass the content, and then save the content to the object store. Let's say we are talking about 10,000 documents per second that we have to crawl. If we assume what each task will look like, the worker has to do an HTTP GET on the URL. They have to pass the document, which will take linear time on the size of the document. There are too many factors, like website latency and if there are errors there will be retries and all those kinds of things.
If we just go with napkin math of one second to do all this work, we are looking at 10,000 machines to support it or 10,000 threads to support it. These machines are not doing any work most of the time. They are just waiting on I/O to get the request back from the server, from where they're downloading stuff from. When that is happening the calculation changes, right? How do we scale, which is not 10,000 machines obviously?
When we are doing event loop-based asynchronous work on each worker, which is waiting on I/O, handing off the requests to the kernel, which is managing these TCP connections. When the response comes back, the kernel is going to wake up and let the event loop know that, "Hey this data is here." The event loop can then pass it on to the CPU, which should not block the event loop and do the CPU-bound parsing logic in a different thread or thread pool.
We are limited by how many TCP connections can be open on the server. As we are talking about, if this event loop is going over, let's say, 1,000 documents per second, I think at this point it is more experimental to see how much we can support. If we try to do some napkin calculation to understand and just get a ballpark of where we might get blocked, if I assume I want each machine to do 1,000 documents per second, we're saying the event loop is able to handle 1,000 documents per second. The server might have 1,000 TCP connections open but wait, the server doesn't need 1,000 TCP connections.It depends on what kind of content the worker is trying to get. If we distribute the work so that content from the same domain is co-located, then it is possible these HTTP requests are getting routed to the same server and the kernel is able to utilize the same TCP connection to download the content. Also if the server supports, say, HTTP/2, then we're talking about multiplexing these TCP connections so a single TCP connection can support multiple requests going through it. We don't pay the cost of the TCP handshake all the time but HTTP/2 suffers from head blocking, which means one slow server can block content from other pages or one slow request can block other pages from being downloaded.
In this case if the server supports QIC protocol then we should support that in our worker because that allows multiplexing without head blocking. With these techniques I think the connection limit won't be an issue for supporting 1,000 documents per second. Let's see what other things can impact this number. Let's talk about the two things:
1. It comes down to mostly network: how much ingress and egress we are doing. Egress, or outgress, we are doing 1,000 documents per second. Let's assume each web page is 10 KB. Then we're talking about 10 Mbps from each worker, which is not high. Modern hardware can easily support 1 to 10 Gbps over the network interface but we are talking about a data center. These servers are hosted in some kind of a rack so the worker doesn't have the full bandwidth to itself. It is maybe sharing it across 10 to 20 racks and 10 to 20 servers in a rack. We are looking at even if we say 50 in a rack then 500 Mbps, which is again well under modern controllers, which can support up to 10 Gbps or even more. I think 1,000 documents per second is pretty manageable.
2. If we are talking about 100K documents per second then we are looking at a fleet of 100 machines, maybe 10% extra for redundancy that we have to support the egress to the object store. There are a lot of techniques if we are using S3 to do part uploads to concurrent uploads to reach the throughput that we need for the object store to do it. Again egress also our network interface should be able to support 100 to 200 Mbps. When we are talking about storing it we can also consider doing a local disk write, which should be much much faster, and then slowly push it to the object store to kind of reduce a direct dependency on keeping these workers busy and always parsing and writing content.

That's it for what I can go over in the interview.
