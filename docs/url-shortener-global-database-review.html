Global URL Shortener — six-page print edition

Page 1 · Foundations

Problem model and consistency vocabulary

Separate uniqueness, read freshness, durability, and physical replication before selecting a database.

Central conclusion A permanent region prefix plus a region-unique suffix creates disjoint primary-key spaces. If that invariant is reliable, global coordination is unnecessary for collision prevention. A global database then solves redirect freshness, latency, and disaster recovery.

Your proposed write path

Generate candidate→Insert if absent→Commit locally→Return slug

Suppose Region A owns use1_ and Region B owns euw1_. The complete keys cannot collide across those regions even when suffixes match. Within Region A, two concurrent requests can still produce use1_aB3x9Q; an atomic database operation must select exactly one owner.

A hash is not collision-free A finite hash is probabilistically unique. Deterministic uniqueness requires a suffix allocated exactly once within its region—for example, an atomic regional sequence or correctly partitioned Snowflake-style ID. Otherwise retain database collision detection.

Four distinct guarantees

Atomic uniqueness Concurrent creators cannot both reserve the same complete slug. A SQL unique constraint or DynamoDB conditional write supplies this.
Read-after-write consistency After creation succeeds, a later read is guaranteed to observe the mapping rather than an older or missing value.
Durability and RPO An acknowledged mapping survives failures. Recovery Point Objective (RPO) zero means failover loses no acknowledged writes.
Replica convergence Every physical replica has eventually applied the write. This is not the same as a strong read being logically able to observe it.

What “globally available” means

Asynchronous replication: the source commits first; another region can temporarily return a missing or old mapping.

Quorum replication: commit waits for enough voting replicas, but not necessarily every replica. A strong read at a lagging copy may coordinate or wait.

Therefore there is no single universal “global propagation latency.” Ask which measurement is required:

  • Time until a strong read can observe the write.
  • Time until an eventual local read observes it.
  • Time until every physical replica applies it.

Routing design improvement

Encode a logical shard or namespace ID rather than a physical region. Keep a small replicated map from logical shard to current owner. This allows evacuation or migration without changing old URLs.

Page 2 · DynamoDB local correctness

DynamoDB as an atomic slug registry

A conditional PutItem is the key-value equivalent of inserting under a unique primary-key constraint.

Table shape

Use slug as the complete partition key. Store the long URL and immutable metadata in the item. DynamoDB hashes the partition-key value internally, so high-cardinality Base62 slugs distribute naturally. Do not use a low-cardinality field such as region or date as the sole partition key.

Atomic insert-if-absent command

aws dynamodb put-item \
  --table-name UrlMappings \
  --item '{
    "slug":       {"S":"use1_aB3x9Q"},
    "destination":{"S":"https://example.com/long/path"},
    "createdAt":  {"S":"2026-08-27T22:14:00Z"},
    "requestId":  {"S":"req-93f07"}
  }' \
  --condition-expression "attribute_not_exists(#slug)" \
  --expression-attribute-names '{"#slug":"slug"}' \
  --return-values-on-condition-check-failure ALL_OLD \
  --region us-east-1

What happens under concurrency

  1. Two requests issue this write for the same absent key.
  2. DynamoDB evaluates each condition as part of the write; there is no application-side gap.
  3. One insertion succeeds.
  4. The other receives ConditionalCheckFailedException.
  5. The losing request generates another candidate and retries.

Do not perform GetItem followed by an unconditional PutItem. Both callers could observe absence and then overwrite one another. Also avoid unconditional UpdateItem for immutable mappings.

Safe retry logic

for attempt in 0..MAX_ATTEMPTS:
  slug = prefix + encode(hash(url, attempt))
  try:
    PutItem(
      key = slug,
      value = { url, requestId },
      condition = attribute_not_exists(slug)
    )
    return slug
  catch ConditionalCheckFailedException:
    continue
  catch TimeoutOrServerError:
    item = StrongGet(slug)
    if item.requestId == requestId:
      return slug
    raise

Error interpretation

ConditionalCheckFailedException: the candidate is occupied; try another candidate.

Timeout or HTTP 5xx: the result is ambiguous. The item might have committed before the response was lost. Strongly read and compare requestId.

Throttling: retry with exponential backoff and jitter; it does not imply a key collision.

ALL_OLD: can return the item that caused the failed condition without a separate read.

ConsistentRead is separate ConsistentRead=true belongs to reads such as GetItem. The write condition already executes atomically. Strong reads are supported on a base table and local secondary index, not on global secondary indexes or DynamoDB Streams.

If the table uses a composite key, existence applies to the complete partition-key and sort-key pair. Two records with different sort keys are different items. A simple slug partition key avoids this loophole.

Page 3 · DynamoDB global behavior

Global Tables: MREC versus MRSC

MREC means multi-Region eventual consistency. MRSC means multi-Region strong consistency.

MREC: asynchronous active-active

Each region has a writable replica. A successful write does not wait for other regions. DynamoDB asynchronously copies changes to all replicas, typically within one second or less, but AWS provides no replication-latency SLA.

Write A→Local success→Async copy→Region B
  • A strong read in B can still be stale relative to a write made in A.
  • A conditional write evaluates the item version currently in its receiving region.
  • Same-item writes in two regions can both initially succeed.
  • Conflicts converge with last-writer-wins using internal timestamps.
  • CloudWatch ReplicationLatency measures source/destination lag; it is not a guarantee.
  • MREC transactions are atomic only in their invocation region and replicate item-by-item.

MRSC: synchronous global authority

Before returning success, DynamoDB synchronously replicates the item to at least one other region. Strong reads on any replica return the globally latest item. Conditional writes evaluate globally current state.

Write A→Cross-region quorum→Success
  • Same-item cross-region races can return ReplicatedWriteConflictException; retry with backoff.
  • Acknowledged writes have RPO zero.
  • Exactly three regions: three full replicas, or two replicas plus a non-serving witness.
  • Regions must be within one supported US, EU, or Asia-Pacific region set.
  • Transactions, TTL, and local secondary indexes are unsupported.
  • The consistency mode cannot be changed after creation.
Why MREC remains correct for your design If Region A can create only its permanent prefix and Region B only a different prefix, they never write the same DynamoDB item. MREC’s cross-region conflict rule is never exercised. A local conditional write handles same-region races.

The remaining issue: temporary remote misses

Immediately after Region A returns a slug, Region B may not yet have it. Treat the first local miss as “possibly replicating,” not as a definitive 404.

item = LocalReplica.GetItem(slug)
if item exists:
  return HTTP 302 Location: item.destination

homeShard = decodePrefix(slug)
item = ReadFromCurrentOwner(homeShard, slug)
if item exists:
  populateLocalCache(item)
  return HTTP 302 Location: item.destination

return HTTP 404

Do not negative-cache until both local and authoritative reads miss. After propagation or cache population, future redirects remain local.

Page 4 · Google Cloud

Cloud Spanner

Global SQL with external consistency and synchronous Paxos replication, but normally leader-centric writes.

Consistency guarantee With default serializable isolation, Spanner provides external consistency: transactions appear serial, and their order agrees with the real-time order in which clients observe commits. A strong read observes every transaction committed before the read began.

How a write commits

Spanner divides ordered primary-key space into ranges called splits. Each split has a Paxos replica group and an elected leader.

Client→Split leader→Voting quorum→Commit
  1. The leader logs the mutation.
  2. Voting replicas receive it in parallel.
  3. A majority accepts the write.
  4. The transaction commits.
  5. Remaining full replicas can apply it afterward.

A successful commit is quorum-durable, not proof every replica has physically applied it.

Strong remote reads

A strong read can reach a read-write or read-only replica. A non-leader replica may consult the leader to establish a safe timestamp and wait for required mutations. The application therefore receives fresh data even while physical convergence continues.

Latency implications

Writer near the leader Avoids an extra client-to-leader WAN path, but still waits for a geographically distributed voting quorum.
Writer in another region Is routed toward the leader. Disjoint keys reduce contention but do not remove WAN routing and quorum latency.
Strong remote read May require leader timestamp negotiation. A sufficiently stale read can usually remain at a nearby replica.
No universal milliseconds Latency depends on region geometry, leader location, quorum response, load, indexes, transaction range count, and read policy.

Uniqueness and regional ownership

Use the slug as the primary key. A normal INSERT fails on a duplicate key; unique indexes are checked at commit. Concurrent creators cannot commit two destinations for one slug. Handle the duplicate result or use an insert-if-absent form whose return semantics are clear.

Standard multi-region Spanner does not automatically give each application region a local write leader. Split leaders normally reside in one configured default leader region. “Writes can originate from multiple regions” means requests are accepted globally, not that they commit independently in each region.

Geo-partitioning and hotspots

Geo-partitioning can place subsets of rows into separate instance partitions with placement-specific leaders while retaining global transactions. As of this research it is Preview, and global indexes can reintroduce distant-quorum latency.

Ordered-key hotspot Spanner stores rows lexicographically. A region prefix followed by an increasing sequence creates one moving hot edge per region. Prefer random high-entropy suffixes or a leading distribution hash. Monotonic secondary indexes can hotspot independently.

Page 5 · Amazon Aurora

Aurora Global Database

A single-writer relational architecture with asynchronous global read replicas.

Aurora Global Database is not active-active There is one primary cluster in one AWS region. Regional secondary clusters are readers. Global write forwarding sends SQL from a secondary to the primary; it does not create an independent regional writer.
Client in B→Secondary endpoint→Primary in A→Commit→Async copy to B

Replication and write latency

Aurora uses storage-level asynchronous replication from the primary cluster to as many as five secondary regional clusters. Primary commits do not wait for those secondary regions. AWS describes replication latency as typically under one second; this is neither a bound nor an SLA.

A writer connected in a secondary region pays network travel to the primary and waits for the forwarded SQL result. If it subsequently reads at the secondary under a stronger consistency mode, it may wait again for replication to return.

URL-shortener behavior

Primary-key and unique-index constraints remain correct because all writes commit at the primary. Disjoint keyspaces improve concurrency but do not make commits local.

A redirect in an unrelated session is not protected by session consistency. It must use global consistency, query the primary, or tolerate a local miss and fall back.

Secondary read consistency

EVENTUAL The query does not wait. It may return old or new data depending on current replication lag.
SESSION The secondary waits for writes forwarded by that same session. It does not include unrelated sessions.
GLOBAL Each query waits until the secondary is caught up with all primary commits that existed when the query began.

Stronger modes convert replica lag into query latency; they do not make underlying replication synchronous.

Failure behavior

EventBehaviorData-loss implication
Planned switchoverSynchronize, then promote a secondaryCan provide RPO zero, with temporary unavailability
Unplanned failoverPromote the selected secondaryUnreplicated primary commits can be lost; RPO depends on lag
Ordinary secondary readServed from asynchronously replicated storageMay be stale unless configured to wait
When Aurora is reasonable Choose it when PostgreSQL/MySQL compatibility is important, writes can be centralized, and worldwide traffic is dominated by reads. It is not the closest match to independently writable regional namespaces.

Page 6 · CockroachDB and decision

CockroachDB and the recommended design

CockroachDB offers explicit table locality; the final database choice follows from your required remote-read behavior.

CockroachDB guarantees

CockroachDB defaults to serializable isolation. Each key range is replicated through Raft and has a leaseholder that coordinates writes and ordinarily serves fresh reads. A successful commit is persisted on a majority of replicas for each affected range.

Applications must retry serialization failures. An ambiguous commit result must be resolved instead of assumed to have failed.

INSERT INTO url_mappings (slug, destination)
VALUES ($1, $2)
ON CONFLICT (slug) DO NOTHING
RETURNING slug;

One returned row means success; no row means occupied. Do not use DO UPDATE merely to simplify retries—it can change an existing slug’s destination.

Table locality choices

REGIONAL BY TABLE One home region for the entire table. Fresh writes and reads are best there.
REGIONAL BY ROW Every row has a home region. This matches encoded ownership: local writes and fresh home reads; remote fresh reads may cross regions.
GLOBAL Fresh reads use a consistent local replica in every configured region. Writes pay cross-region replication and commit-wait.
Follower read A fast local historical read. A newly created mapping can be absent until the selected historical timestamp passes its commit.

There is no fixed global-write latency: gateway-to-leaseholder distance, voter placement, quorum distance, survival goal, clock settings, number of ranges, and load all matter. Region prefixes followed by increasing counters can create hot index tails; use random suffixes or hash-sharded indexes. For REGIONAL BY ROW, set home region explicitly so failover routing does not misplace rows.

Recommended interview answer Use DynamoDB Global Tables MREC for the immutable slug-to-destination mapping. Regional prefixes make keyspaces provably disjoint. Reserve with local conditional PutItem. Redirect from the local replica; on a miss, decode the logical home shard, perform one authoritative fallback read, and populate regional/CDN cache.

When to pay for global coordination

  • The product requires immediate read-after-write in every region with no fallback.
  • The same slug may be created or modified concurrently in multiple regions.
  • RPO zero across regional failure is mandatory.
  • Multi-row SQL transactions are central to URL creation.
