Redis vs ZooKeeper / etcd

Why "they're all key-value stores" is the wrong lens, shown as the concrete sequences in which Redis breaks a lock, a leader election, or a config push, and what ZooKeeper and etcd do differently at the exact step where Redis goes wrong.

The one-sentence answer. Redis is a fast, available key-value store that acknowledges a write when one process has it in RAM. ZooKeeper and etcd are slow, consistent coordination services that acknowledge a write only when a majority of nodes have fsynced it, and that hand you a cluster-wide monotonic version with every read and write. Coordination problems (locks, leader election, membership, config) are precisely the problems where a single lost or stale write is a correctness bug rather than a cache miss.

The last row is why both exist. Redis is fast because it skips exactly the work the other two do for safety. You pay for coordination guarantees in latency, and you only want to pay it on the small, rarely-written control-plane data.

1. What coordination actually requires

Every "config management / service discovery / leader election / distributed lock" use case decomposes into the same five primitives. Hold a design against this list, not against "does it store key-value pairs".

2. Failure 1: an acknowledged write is lost on failover

This is the root failure. Everything else is a consequence of it. Redis replication is asynchronous: the primary replies OK to the client and then, separately, streams the command to replicas. If the primary dies in between, the write existed only in a dead process's RAM.

request / commandreplymessage lost

etcd Same lock, same crash, Raft commit

Where exactly they diverge. Compare step 3 in each diagram. Redis says OK after a memory write on one node. etcd says OK only after a majority has fsynced the entry. That single ordering difference, "ack before replicate" vs "replicate (to a majority) before ack", is the whole story. Raft's Leader Completeness property then guarantees any future leader has the entry, because a node missing a committed entry cannot win a majority vote.

3. Failure 2: split brain during a network partition

Redis Sentinel and Redis Cluster both detect a dead primary by timeout and promote a replica. But the old primary is not dead, it is merely unreachable from the Sentinels. It keeps serving its own clients. Now there are two primaries, and when the partition heals one of them is demoted and resynced from the other, discarding everything it accepted in between. The Redis Sentinel documentation shows exactly this scenario.

Doesn't min-replicas-to-write fix this? It narrows the window. The old primary stops accepting writes once it has fewer than N replicas acknowledging within min-replicas-max-lag seconds (default 10). Everything written in those ~10 seconds is still lost when it is demoted, and if the old primary's side keeps enough replicas the check never fires at all. Toggle the checkbox above and move replicas around to see both cases. This is the Redis docs' own position: the setting "makes the window of lost writes smaller", it does not eliminate it.

4. Failure 3: no fencing token for a paused lock holder

This failure is independent of replication, and it is the one Martin Kleppmann's Redlock critique centres on. A client acquires a lock with a TTL, then stalls (GC pause, VM migration, swapped out, slow network). The TTL expires, another client takes the lock, and then the first client wakes up and keeps working. No lock service can prevent that wake-up. What a coordination service can do is hand every lock holder a monotonically increasing token, so the downstream resource can reject the stale one. Redis does not have such a token; etcd and ZooKeeper do.

Fencing simulator
Why not INCR a counter in Redis and use that as the token? Because the counter lives in the same asynchronously replicated Redis. After the failover in Failure 1 the counter can go backwards, and a token that is not monotonic across failover is not a fencing token. etcd's revision and ZooKeeper's zxid are produced by the consensus log itself, so they are monotonic across any sequence of leader changes. Note Jepsen's 2020 etcd analysis made the same point from the other direction: etcd's lock API is also unsafe as a mutex unless the protected resource checks the revision. The token is only half the mechanism; the storage system has to verify it.

5. Failure 4: missed notifications (config push, lock release, membership)

Service discovery and config management are not "read a key". They are "be told, reliably and in order, every time the key changes". Redis offers Pub/Sub and keyspace notifications, which are fire-and-forget: a message published while a subscriber is disconnected is gone. etcd watches carry a revision and can resume from any revision still in history; ZooKeeper watches are one-shot but ordered with the data and guaranteed not to be silently dropped while the session is alive.

Try: change twice, disconnect, change three times, reconnect. In Redis mode the client stays stale until something polls. In etcd mode the watch resumes from the last revision and replays every missed event in order. In ZooKeeper mode the client gets a disconnect event, re-reads on reconnect, and sees the latest state (intermediate values are not replayed; that is fine for config, and ZK guarantees you never miss the fact that something changed).

Why a missed event is worse than it sounds. For config, a missed event means stale config until the next poll. For a lock queue (waiters watching the holder's key) or leader election (followers watching the leader's ephemeral node), a missed "deleted" event means the waiter never wakes up. The system is stuck with no leader and nobody notices until an alarm fires. Polling "fixes" it at the cost of N clients × poll rate, which is exactly the hot-spot load you were trying to avoid.

6. Failure 5: stale reads with no way to detect them

"Who is the current leader?" is a read. On Redis, if the read goes to a replica it may be arbitrarily stale, and the response contains no version you could compare against anything. On ZooKeeper, a follower may also serve a stale read (reads are sequentially consistent, not linearizable), but every read carries the zxid, and sync() before a read forces linearizability. etcd reads are linearizable by default: the leader confirms it is still leader (ReadIndex) before answering.

7. "But what about…" (objections you will hear in an interview)

WAIT numreplicas timeout

WAIT 1 1000 blocks until at least one replica has acknowledged the write. It raises the odds the write survives, but the Redis docs are explicit that it does not make Redis strongly consistent: Sentinel/Cluster may still promote a replica that did not receive the write (the one that acked may itself be dead or partitioned), and WAIT does not fsync anything (WAITAOF in 7.2 does, locally). Majority ack plus leader completeness is what Raft gives you; WAIT gives you neither.

Redlock

Redlock acquires the lock on N independent Redis masters (majority wins) with a TTL. It fixes the single-node loss in Failure 1 only under timing assumptions: that clocks do not jump and that processes do not pause for longer than the TTL. Kleppmann's critique ("How to do distributed locking", 2016) is that these assumptions are exactly what you cannot make in a real system, and that Redlock has no fencing token (Failure 3). antirez's reply argues the timing assumptions are reasonable in practice. The interview-safe position: Redlock is acceptable for efficiency locks (avoid duplicate work) and not for correctness locks (prevent corruption). The distinction is Kleppmann's and interviewers know it.

Redis Cluster

Changes nothing here. Cluster shards keys across primaries; each shard still uses asynchronous replication and timeout-based failover. The Cluster spec itself says it is "not able to guarantee strong consistency" and gives the lost-write-on-failover example.

"I'll put appendfsync always on"

That makes a single node's writes durable to its own disk. It does nothing for replication or failover, and the acknowledging node's disk is unreachable when that node is the one that is partitioned away.

"I'll just use SET NX with a TTL and accept the risk"

Often the right call, when the thing being protected is idempotent or cheap to redo. State it as a conscious trade: "this is an efficiency lock; duplicate execution is tolerable; I'm choosing Redis for latency and because I already run it". The failure is not choosing Redis, it is choosing it without naming what happens when it lies.

8. How ZooKeeper and etcd actually get there

Both are a replicated log driven by a leader-based consensus protocol, with a small in-memory key-value state machine on top. The guarantees in sections 2–6 all fall out of four mechanical facts:

  1. Every write goes through the leader and is appended to a write-ahead log. No write is acknowledged until a majority of nodes have fsynced it. (ZooKeeper: ZAB proposal + ACK + COMMIT. etcd: Raft AppendEntries + majority match index.)
  2. Elections require a majority, and a voter refuses to vote for a candidate whose log is behind its own. So the new leader always has every committed write. Two sides of a partition cannot both have a majority.
  3. The log index is exposed as a version. ZooKeeper: zxid (64-bit, epoch + counter) and per-znode version. etcd: a cluster-wide revision that increments on every transaction, plus per-key mod_revision. These are your fencing tokens and your CAS targets.
  4. Liveness is bound to the server-side notion of a client, not to a key TTL that a client refreshes. ZooKeeper: a session with heartbeats; ephemeral znodes vanish when the session expires, atomically and in log order. etcd: a lease with a TTL and keepalives; keys attached to a lease are deleted when it expires, as a logged transaction (so watchers see it at a specific revision).

10. When Redis is the right answer

None of the above says Redis is bad. It says Redis is a data-plane store, not a control-plane store. Reach for Redis when the question is throughput, latency, or data size and a lost or stale value is a performance event rather than a correctness event.

Use caseWhy Redis fitsWhat a lost write costs
CacheSub-ms, 100k+ ops/s, eviction policiesA cache miss
Session storeFast reads on every requestA user logs in again
Rate limitingINCR + EXPIRE, Lua for sliding windowsA few extra requests get through
Leaderboards, counters, geo queriesSorted sets, HyperLogLog, GEOSlightly wrong number
Pub/Sub fan-out, StreamsMillions of messages/sAt-most-once (Pub/Sub) or redelivery (Streams)
Efficiency lock / de-dupSET NX PX, cheapDuplicate work happens occasionally

The common real-world architecture: etcd or ZooKeeper holds who is leader and which shards exist (kilobytes, a few writes a second). Redis holds the data those leaders serve (gigabytes, tens of thousands of writes a second). Never route data-plane traffic through the coordination service: a 5-node etcd cluster will fall over around 10k writes/s and every write pays a cross-node fsync.

12. Interview phrasing and cheat sheet

Say it proactively, in one breath, before the interviewer asks "why not Redis":
"For the coordination piece, leader election and shard ownership, I want a store whose acknowledgement means a majority has durably committed the write, that gives me a monotonic revision I can use as a fencing token, and whose watches can't silently drop a change. That's etcd or ZooKeeper, and it only has to handle a few writes a second. Redis acks on one node's RAM with async replication, so an acked lock can vanish on failover and both sides of a partition can accept writes. I'll still use Redis for the hot data path, where a lost write is a cache miss, not a correctness bug."

Follow-ups you should be ready for, with the one-line answer:

  • "Can't WAIT fix it?" No majority election semantics; a replica that never got the write can still be promoted.
  • "What about Redlock?" Fine for efficiency locks; no fencing token and timing-dependent, so not for correctness locks.
  • "Doesn't etcd have the GC-pause problem too?" Yes. Nothing prevents a stale holder from waking up. etcd gives you the revision so the resource can reject it. The resource must check.
  • "Why not put everything in etcd then?" Every write is a cross-node fsync. ~10k writes/s, small values, and compaction to manage. It is a control plane.
  • "ZooKeeper or etcd?" Same guarantees. ZK if the ecosystem already has it or you want sequential ephemeral nodes; etcd if greenfield, k8s-adjacent, or you want resumable watches and linearizable reads by default.
  • "How does the leader know it is still the leader?" It doesn't, in the absolute. It holds a lease/session and must stop acting when it cannot renew within the timeout, and downstream writes carry the fencing token.

13. Worked design: graceful drain with gradual session migration

Scenario: five nodes on a consistent hash ring; sessions hash to one of 4096 partitions and partitions are assigned to nodes by the ring. Node1 is asked to shut down. It must stop taking new sessions but keep serving and holding state for its existing sessions until each has been handed off. A session-manager leader (elected via etcd) drives the migration; standby session managers see the same etcd state but do nothing until one of them becomes leader.

One change to the stated design: Node1 must not give up its lease at the start. A lease that disappears is indistinguishable from a crash, and the crash path (instant reassignment, state rebuilt or lost) is exactly what a graceful drain is trying to avoid. Instead Node1 keeps its lease alive and flips its registration to DRAINING. It revokes the lease only after the last session has moved. If Node1 dies mid-drain, the lease expires and the leader falls back to the crash path for whatever had not migrated yet, which is the correct degradation.

Design notes that the diagram relies on

  • The coordination unit is the partition, not the session. Sessions hash to one of a fixed number of partitions (4096 here; Redis Cluster uses 16384 slots, Cassandra uses vnodes, Kafka uses partitions). etcd holds /partitions/Pn = {owner, epoch, state}: thousands of keys, two writes per partition per move. A design that writes a key per session into etcd does not survive a million sessions, and migrating 10k sessions an hour would be 10k consensus writes an hour for no benefit.
  • Two rings during a drain. The routing ring (epoch 100) still includes Node1, so existing partitions stay reachable. The placement ring (epoch 101) excludes Node1, so no new session lands there. Both live in the one /ring key; routing flips at the end.
  • Per-partition state machine: STABLE(node1) → MIGRATING(node1→node3) → STABLE(node3). While MIGRATING, the source serves sessions it still holds and answers ASK target for ones already moved; the target serves what it has and bounces (or pulls on demand) what it does not. This is Redis Cluster's slot-migration protocol (CLUSTER SETSLOT … MIGRATING / IMPORTING, ASK redirects), and it is safe to name as the precedent.
  • The per-session loop is pairwise. Source freezes the session, transfers, target acks and serves. Only two nodes are ever involved and both carry the partition epoch, so at most one node serves a session at any instant without any central record of that session.
  • Fencing token = partition epoch. Every write to the durable session store carries it; the store rejects a lower epoch for that partition. A Node1 that missed the handoff cannot overwrite Node3's work.
  • Every leader write is a Txn conditioned on the leader key. If create_revision(/leader/sm) == <my election revision>. A deposed leader cannot corrupt the ring or partition map.
  • Leader only sequences; it is not on the data path. It chooses which K partitions are MIGRATING at once (the gradualness knob) and records transitions. If it dies, in-flight partition migrations keep going; the new leader reads the /partitions/ prefix and resumes.
  • Standbys watch, never act. Their view is warm; on leader-key expiry one campaigns and continues.
  • Clients heal by redirect. ASK during migration, partition-map watch for the final flip. No central "where is session_i" lookup on the hot path.
  • Crash degradation. Node1 dying mid-drain expires its lease; the leader sets its remaining partitions to their ring-101 owners at a higher epoch; targets rebuild missing sessions from the durable store. Graceful degrades to crash semantics, never to two owners.
