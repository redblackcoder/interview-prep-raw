A guided re-read

“The Log,” Part 4: System Building — one layer at a time

Part 4 is where many readers lose the thread: Kreps mixes a big-picture philosophy about the future of databases with a concrete engineering mechanism, and jumps between them. This page separates the two — we build the machine first, one idea per layer, then zoom out to the philosophy once the parts are on the table.

Re-organized from Jay Kreps, “The Log: What every software engineer should know about real-time data's unifying abstraction” (Dec 16, 2013). All ideas are his; only the ordering and diagrams are new.

The one sentence to hold onto: A distributed data system can be split into two parts — a log (the source of truth: an ordered record of every change) and a serving layer (indexes that answer queries). Almost everything hard — consistency, replication, recovery, rebalancing — belongs to the log. What's left over, the query API and index shape, is the only part that should differ between systems.

0 The thesis, in one picture

Kreps' claim: the log does the same job inside a single distributed database that it does across a whole organization (Parts 2–3). “What, after all, is an organization, if not a very complicated distributed data system?” So we can factor any such system like this:

1 The simplest working system

Layer 1 · writes + one index

Start with the smallest thing that works. A writer appends changes to the log; the log assigns each a sequential timestamp (its position). One serving node subscribes to the log, reads changes in order, and applies each to its own local index (a B-tree, an SSTable, an inverted index — whatever it needs to answer its queries).

Why this already matters

Two things a state machine needs (from Part 1) fall out for free: everything is ordered, and the index is reconstructable — lose the serving node and you can rebuild its index by replaying the log. The log is the truth; the index is disposable.

2 Scale it: partitions & replicas

+ adds: horizontal scale & fault tolerance

One log and one node don't scale. So partition the log (Part 3's trick), and give the serving layer the same number of partitions — though it may run on a different number of machines. Each log partition can also be replicated to several serving nodes, each keeping an identical copy of that partition's index.

3 Reads without a leader (the timestamp trick)

+ adds: correct reads, no leader election

Serving nodes replay the log “as quickly as possible,” so a replica may be slightly behind. How do you avoid serving stale data right after a write? The client carries the write's timestamp into its query. A serving node compares that timestamp to how far it has indexed, and waits if it hasn't caught up yet. This gives read-your-writes from any replica.

4 Recovery & rebalancing, for free

+ adds: restore failed nodes, move partitions

The trickiest chores in a distributed system — restoring a dead node, or moving a partition to a new machine — become replay problems. Two options: keep a fixed window of recent log + a periodic snapshot of the partition, or keep a complete (compacted) log and rebuild from scratch. Either way, the messy, stateful recovery logic moves out of the system-specific serving layer and into the general-purpose log.

Tally: what the log does, so the serving layer doesn't have to

  • Sequences concurrent updates → consistency (eventual or immediate)
  • Replication between nodes
  • “Commit” semantics — acknowledge a write only once it can't be lost
  • An external subscription feed out of the system
  • Restore failed replicas & bootstrap new ones
  • Rebalance data between nodes
That's most of what a distributed data system is. What remains is just the query API + index shape — the part that legitimately differs (a full-text search hits every partition; a key lookup hits one).

5 One log, many indexes → back to data integration

+ adds: the link to Parts 2 & 3

Here's where Part 4 reconnects to the rest of the essay. Since the log already exposes a subscription feed, many different systems can share one log, each building the index it's good at. And a log-fed system is itself a stream source — a stream processor can consume feeds and serve its output through yet another index.

6 Now zoom out: “unbundling the database”

Only after the mechanism is clear does Kreps' philosophy land. If every query system is “just an index,” then your whole organization looks like one giant distributed database — Redis, Solr, Hive, a stream processor: all just different indexes and materialized views over a shared log. Why do we have so many separate systems? Because building distributed systems is hard, so each one narrows its scope to stay feasible. He sees three ways this could go:

Future 1

Status quo

Systems stay separate. Then cross-system data integration via an external log stays one of the most important problems.

Likely for a while
Future 2

Re-consolidation

One general “uber-system” absorbs every function — you'd run one, not a dozen. No integration problem left.

He thinks: unlikely
Future 3 · his favorite

Unbundling

Infra decomposes into reusable open-source blocks. Assemble systems Lego-style; if build time drops from years to weeks, the pull toward one monolith disappears.

The appealing path

“Unbundling” = distributed-systems Lego

7 Two objections he heads off

“Keeping a whole extra copy in the log is wasteful!”

Not really, for three reasons: (1) the log does only linear reads/writes, so it's happy on cheap multi-TB spinning disks (LinkedIn stored 75 TB/datacenter on Kafka), while serving systems burn expensive RAM/SSD; (2) that cost is amortized across every index that shares the log; (3) the log is simply a very efficient storage shape. Net expense: minimal.

“Doesn't the log have to be strongly consistent?”

No. Kafka/BookKeeper happen to be consistent logs, but you could factor a Dynamo-style, eventually-consistent (AP) log + a key-value serving layer. Such a log redelivers old messages and pushes reconciliation onto the subscriber — trickier, but the same two-part factoring still holds.

8 How LinkedIn actually ran this

Not theory — production

LinkedIn's search, social graph, and OLAP systems were all built this way: each feeds off a database change-log (via Databus) or a dedicated Kafka feed, then adds its own partitioning + index + query API. A single feed is often replicated into several serving systems at once.

The radical part: those serving systems have no external write API at all. Kafka and the databases are the system of record; each node “blindly transcribes” its partition's feed into local storage, and a dead node is restored by replaying the upstream log. Taken to the limit, the serving tier is “nothing less than a sort of cache” — writes go straight to the log, and the index is just a fast, rebuildable view of it.

The 30-second recap

  1. Factor the system into a log (ordered truth) + a serving layer (indexes).
  2. Layer 1: writes go to the log; a node subscribes and builds an index that's a replayable projection.
  3. Layers 2–4: partition + replicate for scale/HA; get correct reads via a write-timestamp (so no leader election needed); recover and rebalance by replaying snapshot + log tail.
  4. The log therefore owns consistency, replication, commit, subscription, recovery, rebalancing — leaving only the query API + index shape to vary per system.
  5. Layer 5: one log, many indexes → this is the same data-integration idea from Parts 2–3, now inside one system.
  6. Zoom out: the org is one big database; every store is “just an index.” Kreps bets on unbundling — assembling systems from reusable blocks, with the log as a commoditized building block.
  7. Objections (wasteful copy? must it be consistent?) both dissolve; LinkedIn ran exactly this, with serving tiers as write-API-less caches over the log.
